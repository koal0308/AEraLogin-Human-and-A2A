🛡️ AEra Security Concept

Sybil-Resistance & Bot-Prevention Architecture

Phase 1: Beta Active Phase 2: Production Coming Soon

📋 Executive Summary

AEra implements a two-phase security model that combines cryptographic proof, social validation, and blockchain transparency to prevent fake accounts, spam, and bot attacks while maintaining a frictionless user experience.

Current Status: Phase 1 (Market Entry - Frictionless Onboarding)

Future: Phase 2 (Community Gate - Resonance Score Threshold)

🤖 Scope: Human Identity Layer

This document covers the security of the human identity layer: Proof of Human, the Identity NFT and Sybil resistance. Autonomous agents and external A2A peers are separate identities with their own security model:

  • Agent identity security: owner-signed lifecycle, Ed25519 challenge–response, audience-bound Agent JWTs, cascading revocation.
  • A2A gateway security: scoped, expiring and revocable peer credentials, replay protection, rate limiting.
  • Trust assessment: evidence-based monitoring of external peers. It is not an access-control mechanism.

🧱 Security Layers: Four Separate Authentication Levels

AEraLogIn separates four relationships. Each has its own credential, and none of them can be substituted for another.

LevelWho authenticates to whomMechanismCannot do
1Human / Owner → AEraLogInWallet signature (EIP-191, EIP-1271 for smart wallets) over a server-issued nonce. Login nonces are stored server-side, bound to the address, expire after 10 minutes and are single use. The dashboard session uses a separate server-stored challenge (5 minutes, single use). Agent lifecycle actions additionally require an owner signature over a single-use, operation-bound challenge.A dashboard session alone cannot register, rotate or revoke an agent key.
2AEraLogIn → RuntimeOne-time enrollment code (short-lived, single use, bound to the owner). The runtime generates its Ed25519 key locally; the private key never leaves the machine. The server only stores the public key.An enrollment code cannot be reused, and it cannot be claimed for another owner.
3Agent → Agent (A2A, internal)Ed25519 challenge–response → short-lived Agent JWT (issuer, audience and jti bound). Revocation applies on the next request.A revoked or foreign agent cannot relay messages. The JWT is not accepted as a dashboard session.
4External peer → GatewayOwner-issued peer credential (aera_a2a_…). It is scoped to agents and skills, expires, and can be revoked. Only a hash is stored. The peer_id is minted by AEraLogIn and stays the same when the credential is rotated.An external peer never becomes an internal agent. Its trust score does not widen its scope.

Gateway → Runtime (internal channel): the gateway reaches a runtime only through a local Unix socket, derived from the agent id, in a directory that only the service user can access. Each request is authenticated with an HMAC envelope. A reply is accepted only if it is signed with an active registered Ed25519 key of the target agent and carries the same agent id and request id. Replies signed with a revoked key are rejected.

Known limitations

  • Trust assessment of external peers is monitoring only. It does not change any access decision, and trust enforcement is not enabled. The public instance runs in the default mode: evidence is recorded, but no assessment is computed on the request path.
  • No automatic installer: the agent runtime is set up by the operator. Anyone with access to the runtime host can use its key.
  • No in-place key recovery after the runtime key is lost. Recovery means re-enrolling, which produces a new agent.
  • Peer credentials are bearer secrets. Whoever holds one can use it until it expires or is revoked.
  • Rate limiting runs in memory per process and is not shared across several server instances. The same applies to pending login nonces: a server restart means users request a new nonce.
  • No external audit has been done yet. The results above come from the project's own test tooling.

🎯 Core Security Principles

1. Blockchain as Single Source of Truth

  • All critical data lives on-chain (Identity NFTs, Resonance Scores, Interactions)
  • Database serves only as performance cache
  • Transparent, immutable, publicly auditable

2. Cryptographic Proof of Ownership

  • Every action requires MetaMask signature (personal_sign)
  • No passwords, no KYC, no personal data
  • Wallet = Identity = Proof of Human

3. Social Validation Network

  • Resonance Score = Own Activity + Follower Validation
  • Bots have high scores but zero social proof
  • Community self-regulates through transparency

📊 Two-Phase Security Model

🚀 Phase 1: Market Entry (Current - Beta)

Goal: Frictionless onboarding for early adopters

✅ Active Security Features:

  1. MetaMask Signature Requirement
    • Every login requires active signature
    • Challenge-Response with unique nonce
    • Cannot be bypassed or automated
  2. Identity NFT (Gasless Mint)
    • Backend pays gas fees
    • User only signs transaction
    • Soul-bound token (non-transferable)
  3. Score Growth Rate-Limiting
    • Maximum +1 point per 60 seconds
    • Cap at 100 points maximum
  4. Self-Follow Prevention
    • Users cannot follow themselves
    • Prevents self-boosting attacks
  5. Blockchain Transaction Recording
    • All interactions logged on-chain
    • Publicly verifiable via BaseScan
    • Immutable audit trail

⚪ Intentionally Open (For Beta Testing):

  • No NFT Score-Gating - Anyone can mint Identity NFT
  • No Resonance Threshold - All users can access private communities
  • Purpose: Allow first users to experience the full flow

🔐 Phase 2: Community Gate (Future - Production)

Goal: Sybil-resistant community access via Resonance Score

🔐 Enhanced Security Features:

1. Resonance Score Threshold

MIN_RESONANCE = 110  # Threshold for gate access

# Gate Check Algorithm
def check_gate_access(address):
    # Step 1: Verify Identity NFT (on-chain)
    has_nft = web3_service.has_identity_nft(address)
    
    if not has_nft:
        return "Access Denied: No Identity NFT"
    
    # Step 2: Calculate Resonance Score
    # own_score = User's individual engagement score (0-100)
    # avg_follower_score = Average score of all followers
    total_resonance = own_score + avg_follower_score
    
    if total_resonance < MIN_RESONANCE:
        return f"Access Denied: Score {total_resonance}/110 required"
    
    return "Access Granted"

2. Resonance Score Composition

total_resonance = own_score + avg_follower_score

# avg_follower_score = SUM(follower_scores) / follower_count

# Example Scenarios:
# Bot:              100 + 0   = 100  (DENIED: No social proof)
# Real Creator:     56  + 54  = 110  (GRANTED: Active + validated)
# Popular Creator:  70  + 65  = 135  (GRANTED: Highly resonant)
# New User:         50  + 0   = 50   (DENIED: Not yet active enough)

3. Social Proof Mechanism

No artificial rate limits needed! The Resonance Score itself acts as the natural gate:

  • Quality over Quantity: High-scoring followers boost resonance more
  • Organic Growth: Real communities naturally accumulate engaged followers
  • Bot Prevention: Fake followers (score 50-60) provide minimal boost
  • Transparency: Blockchain reveals suspicious patterns

📊 Example: 100 real followers (avg score 65) = 165 resonance vs. 1000 bots (avg score 50) = 150 resonance

🤖 Attack Scenarios & Defenses

Scenario 1: Bot Auto-Login Spam

Attack:

// Bot tries to spam logins
for (let i = 0; i < 1000; i++) {
    fetch('/api/verify', {
        body: JSON.stringify({
            address: botWallet[i],
            signature: "fake_signature"
        })
    });
}

Defense:

Signature Verification:

recovered_address = Account.recover_message(message, signature=signature)
if recovered_address != address:
    return {"error": "Signature verification failed"}  # ❌ BLOCKED

Result: ❌ Bot cannot generate valid ECDSA signatures without MetaMask

Scenario 2: Score Farming Bot

Attack:

// Bot logs in every 60 seconds
setInterval(() => {
    await metamask.request({method: 'personal_sign', ...});
}, 60000);

Defense (Phase 1):

Score grows slowly: +1 per minute = 100 points in ~2 hours

Defense (Phase 2):

High score BUT no followers = DENIED

# Bot scenario:
own_score = 100  # Spam-Logins in 2 hours
avg_follower_score = 0  # No followers
total_resonance = 100 + 0 = 100

# Gate threshold: 110
if total_resonance < 110 and follower_count == 0:
    return "🚨 Access Denied: Need Resonance Score ≥110"

Result: ⚠️ Bot reaches Score 100 but cannot access gate (needs 110 total resonance = own score + follower average)

Scenario 3: Fake Follower Network

Attack:

// Bot creates 1000 wallets, follows Creator X
for (let i = 0; i < 1000; i++) {
    await follow(creatorX, botWallet[i]);
}

Defense (Phase 2):

  • Resonance Score Requirement: Creator needs total_resonance ≥110
  • Follower Quality Matters: Fake followers with score=50 provide minimal boost
  • Social Proof Required: Real engagement from real humans needed

Result: 1000 fake followers with score 50 each → avg_follower_score = 50
Bot creator: own_score 100 + avg 50 = 150 (GRANTED but suspicious)
Real creator: own_score 70 + avg 65 = 135 (GRANTED with authenticity)

📊 Blockchain transparency reveals bot patterns post-facto. Community can see suspicious rapid follower acquisition.

Scenario 4: Self-Follow Exploit

Attack:

// User follows themselves to boost score
await follow(myWallet, myWallet);

Defense:

if owner_wallet == follower_address:
    return {"error": "You cannot follow yourself!"}  # ❌ BLOCKED

Result: ❌ Impossible to self-boost

All users can verify any account:

# Check user's blockchain history
interactions = await web3_service.get_user_interactions(address)

# Red Flags:
# 1. Score 100, but interactions = [] (no real activity)
# 2. 50 logins in 2 hours (bot pattern)
# 3. High score, 0 followers (no social validation)

Resonance Score as Authenticity Metric

Phase 1 (Current): Resonance Score is visible but not enforced as gate

// Phase 1: Display only - no restrictions
total_resonance = own_score + avg_follower_score

🔄 Migration Path: Phase 1 → Phase 2

Activation Strategy

When to activate Phase 2:

  • ✅ 500+ active users
  • ✅ Community feedback collected
  • ✅ Bot patterns analyzed
  • ✅ Threshold fine-tuned based on real data

Activation Process

# Feature Flag in .env
RESONANCE_GATE_ENABLED=false  # Phase 1 (current)
RESONANCE_GATE_THRESHOLD=110  # For Phase 2

# Code implementation:
if os.getenv("RESONANCE_GATE_ENABLED") == "true":
    # Phase 2: Enforce Resonance Score check
    # total_resonance = own_score + avg_follower_score
    if total_resonance < 110:
        return {"allowed": False, "reason": f"Need {110 - total_resonance} more resonance"}
else:
    # Phase 1: Only NFT check (current)
    if has_identity_nft:
        return {"allowed": True}

Grandfathering Policy

Option 1: Grandfather all early users

if user['created_at'] < PHASE2_ACTIVATION_DATE:
    return {"allowed": True, "grandfathered": True}

Option 2: Grace period (30 days to reach threshold)

if user['created_at'] < PHASE2_ACTIVATION_DATE:
    grace_period_end = PHASE2_ACTIVATION_DATE + timedelta(days=30)
    if now < grace_period_end:
        return {"allowed": True, "grace_period": True}
