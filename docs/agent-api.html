Agent API

The Agent API gives autonomous agents their own cryptographic identity, owned by a human AEra identity but independent of any human login, OAuth token or browser session.

A human owner registers an agent with a wallet signature. The agent then proves who it is with its own Ed25519 key and receives a short-lived Agent JWT, which it uses to call AEra and to send signed messages to other AEra agents.

Human ownerAEra identity · wallet signature (EIP-191 / EIP-1271)
▼ registers & controls
Agent identitydid:aera:agent:… · Ed25519 public keys
▼ proves possession of key
Agent runtimeholds the private key · never sent to AEra
▼ challenge → signature
Agent JWT15 minutes · audience-bound · revocable
Base URL

All endpoints live under https://aeralogin.com/api/agents. Requests and responses are JSON.

Availability

The Agent Identity Layer is an additive subsystem that the AEra operator can switch on or off. When it is disabled, these routes are not served. Most developers use it through the agent section of AEra Core, which runs the owner steps with your wallet.

🧩 Concepts

ConceptWhat it is
OwnerThe wallet of a human AEra identity. Every lifecycle change needs a fresh owner signature. Externally owned accounts (EIP-191) and smart-contract wallets (EIP-1271) are supported.
Agent IDA stable identifier of the form did:aera:agent:<32 hex>, assigned by AEra at registration. It does not change when keys rotate.
KeyAn Ed25519 public key, encoded as ed25519:<base64url, no padding>, identified by a key_id (aera-key-…). Up to 5 active keys per agent.
CapabilitiesServer-recorded permissions of the agent. The owner sets them; the agent cannot grant itself any.
AudienceWhat a token is for: aera-agent-api (API calls) or aera-agent-relay (message relay). A token only works for its own audience.
Agent runtimeThe process that is the agent. It generates and keeps the private key, authenticates to AEra and answers A2A messages. AEra only ever sees the public key.
Human identity ≠ agent identity

An agent is owned by a human, but it never uses the human's session, OAuth token or wallet key. Agent JWTs and human OAuth tokens are separate credentials, and neither is accepted in place of the other.

🔐 Authentication

The API uses two separate proofs, depending on who is acting:

Owner actions

Register, add / rotate / revoke keys, revoke the agent and change capabilities. Proven with an owner challenge signed by the owner wallet. Each challenge is valid for 120 seconds, can be used once and is bound to one owner, one operation and one agent.

Agent actions

Verify tokens, record interactions and send messages. Proven with an Agent JWT in the Authorization: Bearer header, obtained through an Ed25519 challenge–response. Messages additionally carry their own Ed25519 signature.

🔗 Enrollment — the normal way to create an agent

Enrollment pairs an agent runtime with your dashboard. The runtime generates its Ed25519 key locally; AEra receives only the public key and a proof-of-possession signature. The private key never leaves the runtime.

  1. Create Agent in the agent section of AEra Core. The dashboard calls POST /api/dashboard/agents/enrollments with your session and shows an enrollment code once. It is valid for 15 minutes and can be claimed once.
  2. On the machine that will run the agent: python -m agent_runtime enroll <code> (see Run the agent runtime).
  3. The runtime generates the key, signs the proof of possession and calls POST /api/agents/enrollments/claim.
  4. Dashboard and runtime show the same key fingerprint (XXXX-XXXX-XXXX-XXXX-XXXX, the first 80 bits of SHA-256 over the public key). Compare them: a match proves AEra received the key your runtime generated.
  5. You approve with your wallet. The dashboard signs an owner challenge with operation: "register" and agent_id: "enrollment:<enrollment_id>" and calls POST /api/agents/enrollments/{enrollment_id}/complete.
  6. AEra creates the agent (agent_id + key_id). The runtime picks both up via POST /api/agents/enrollments/status and stores them in an identity file, so python -m agent_runtime run needs no manual IDs.
Claim request (sent by the runtime)
{
  "enrollment_code": "aera-enroll-<id>.<secret>",
  "public_key": "ed25519:<base64url public key>",
  "signature": "<base64url Ed25519 signature over the enrollment PoP payload>"
}

The PoP payload is the canonical JSON of protocol (aera-agent-enroll), version, enrollment_id, public_key and domain. It binds the signature to this enrollment and this key.

PropertyBehaviour
Secret storageOnly a SHA-256 hash is stored, and it is compared in constant time. The code is never shown again.
Single useOne claim, one completion. A second claim, or reusing a code, returns 409.
Wrong codeAn unknown ID and a wrong secret give the same 404 invalid_enrollment_code.
Bad proof of possession401 invalid_proof_of_possession. The enrollment stays claimable.
Expired / cancelled410 enrollment_expired / 409. An owner can cancel an open enrollment with DELETE /api/dashboard/agents/enrollments/{id}.
Owner bindingOnly the owner who created the enrollment can complete it. A plain register challenge cannot complete an enrollment.
LimitsUp to 5 open enrollments per owner. Claim: 30/min per IP and 10/min per enrollment. Status: 120/min per IP and 60/min per enrollment. Complete: 10/min per owner.

▶️ Run the agent runtime

No installer yet

The runtime is the agent_runtime module in the repository and runs from the source tree with Python 3.11 on Linux or macOS.

Shell
git clone https://github.com/koal0308/AEraLogin-Human-and-A2A.git
cd AEraLogin-Human-and-A2A
python3 -m venv venv && . venv/bin/activate
pip install -r requirements-dev.txt

export AERA_BASE_URL="http://127.0.0.1:8840"               # example: your AEra instance
export AERA_RUNTIME_KEY_PASSPHRASE="<choose a passphrase>"   # encrypts the key at rest
export AERA_RUNTIME_INTERNAL_SECRET="<same value as the AEra server>"

python -m agent_runtime enroll aera-enroll-<id>.<secret>
python -m agent_runtime run
python -m agent_runtime health
  • The key is stored at AERA_RUNTIME_KEY_PATH (default ~/.aera/agent_key.json, mode 0600). It is sealed with scrypt and AES-GCM if a passphrase is set, and stored unencrypted otherwise.
  • The identity file next to it (agent_key.identity.json, 0600) contains only agent_id, key_id and the base URL. If AERA_RUNTIME_AGENT_ID or AERA_RUNTIME_KEY_ID is set, the identity file is ignored.
  • run requires AERA_RUNTIME_INTERNAL_SECRET. Gateway and runtime must also use the same AERA_RUNTIME_DIR, where the socket lives. The default provider is mock, which needs no API key.
  • Same host. The A2A gateway reaches the runtime over a local Unix socket, so a runtime can only receive A2A traffic when it runs on the same host as the AEra server. Enrollment and Agent JWT authentication work over HTTP from anywhere.
  • Exit codes: 2 configuration error, 1 key, identity or connection error, 3 agent or key revoked.
  • The enrollment code passed on the command line is visible in shell history and ps until it is used or expires.

Recovery. If you lose the runtime, you have two options. Revoke the old agent and enroll again, which creates a new agent_id. Or, on the advanced path, add a new key to the same agent with POST /api/agents/{agent_id}/keys, revoke the lost key, and start the runtime with explicit IDs. Enrollment cannot rotate the key of an existing agent.

POST /api/agents/owner-challenge

Requests a single-use challenge for one owner operation. operation is one of register, key_add, key_rotate, key_revoke, agent_revoke, capabilities. agent_id is required for every operation except register.

Request
{
  "owner_wallet": "0xYourWalletAddress",
  "operation": "register"
}
Response 200
{
  "challenge_id": "…",
  "challenge": "…",
  "expires_at": "2026-01-01T12:02:00Z",
  "domain": "aeralogin.com",
  "protocol": "aera-owner-challenge",
  "version": "1",
  "owner_wallet": "0xyourwalletaddress",
  "agent_id": "",
  "operation": "register"
}

The owner signs the canonical JSON of this challenge (fields protocol, version, owner_wallet, agent_id, operation, challenge_id, challenge, expires_at, domain, keys sorted) with personal_sign. The hex signature is then sent as owner_signature in the owner request.

Rate limit: 30 requests per minute per owner wallet.

POST /api/agents/register

Advanced / developer path. Most users should use enrollment instead. This endpoint creates a new agent owned by the signing wallet, with its first active Ed25519 key. Generate the key pair inside the agent runtime (for example with python -m agent_runtime keygen) and submit only the public key.

Request
{
  "owner_wallet": "0xYourWalletAddress",
  "owner_challenge_id": "<challenge_id>",
  "owner_signature": "0x<owner signature>",
  "public_key": "ed25519:<base64url public key>",
  "label": "My research agent",
  "capabilities": ["agent.authenticate", "agent.read.profile", "agent.communicate"]
}
Response 200
{
  "agent_id": "did:aera:agent:<id>",
  "key_id": "aera-key-<id>",
  "capabilities": ["agent.authenticate", "agent.read.profile", "agent.communicate"]
}

label and capabilities are optional. Without capabilities, the defaults agent.authenticate, agent.read.profile and agent.communicate apply. Rate limit: 10 registrations per minute per owner.

🔑 Key management

Each owner operation needs its own owner challenge with the matching operation and agent_id.

POST /api/agents/{agent_id}/keys — add a key

Request (operation: key_add)
{
  "owner_wallet": "0xYourWalletAddress",
  "owner_challenge_id": "<challenge_id>",
  "owner_signature": "0x<owner signature>",
  "public_key": "ed25519:<new public key>"
}

Returns {"key_id": "aera-key-…"}. Fails with too_many_active_keys above 5 active keys.

POST /api/agents/{agent_id}/keys/rotate — rotate a key

Request (operation: key_rotate)
{
  "owner_wallet": "0xYourWalletAddress",
  "owner_challenge_id": "<challenge_id>",
  "owner_signature": "0x<owner signature>",
  "new_public_key": "ed25519:<new public key>",
  "revoke_key_id": "aera-key-<old key>"
}

Adds the new key, revokes the old key and revokes every Agent JWT issued for the old key, all in one transaction. The agent ID stays the same.

DELETE /api/agents/{agent_id}/keys/{key_id} — revoke a key

Body: owner_wallet, owner_challenge_id, owner_signature (operation key_revoke). Revokes the key and cascades to all of its active tokens. Returns {"status": "revoked"}.

Rate limit for all key operations: 20 per minute per agent.

DELETE /api/agents/{agent_id}

Revokes the agent permanently (operation agent_revoke). All of its keys and all active Agent JWTs are revoked in the same transaction. A revoked agent cannot authenticate again.

Request
{
  "owner_wallet": "0xYourWalletAddress",
  "owner_challenge_id": "<challenge_id>",
  "owner_signature": "0x<owner signature>"
}

PATCH /api/agents/{agent_id}/capabilities

Replaces the agent's capability set (operation capabilities). Only these values are accepted. Unknown values are dropped, and if nothing valid remains, the default set applies.

CapabilityAllows
agent.authenticateObtaining an Agent JWT
agent.read.profileHaving its public profile read, including through the A2A gateway
agent.communicateSending and receiving agent messages
agent.interaction.recordRecording signed interactions

Capabilities are issued by the server only. The capabilities in a JWT are always a subset of those recorded for the agent.

🤖 Agent challenge & authenticate

POST /api/agents/{agent_id}/challenge

Request
{ "key_id": "aera-key-<id>", "aud": "aera-agent-api" }

Returns a challenge that is valid for 60 seconds, can be used once and is bound to agent_id, key_id and aud:

Response 200
{
  "protocol": "aera-agent-auth",
  "version": "1",
  "agent_id": "did:aera:agent:<id>",
  "key_id": "aera-key-<id>",
  "challenge_id": "…",
  "challenge": "…",
  "aud": "aera-agent-api",
  "issued_at": "…",
  "expires_at": "…"
}

POST /api/agents/{agent_id}/authenticate

The runtime signs the canonical JSON of the challenge object above (keys sorted, UTF-8) with its Ed25519 private key and sends the base64url signature:

Request
{
  "challenge_id": "…",
  "key_id": "aera-key-<id>",
  "aud": "aera-agent-api",
  "signature": "<base64url Ed25519 signature>"
}
Response 200
{
  "token": "<Agent JWT>",
  "jti": "…",
  "aud": "aera-agent-api",
  "expires_at": 1767269700,
  "capabilities": ["agent.authenticate", "agent.read.profile", "agent.communicate"]
}

Rate limit: 60 challenges and 60 authentications per minute per agent.

🎫 Agent JWT

An Agent JWT is valid for 15 minutes and only for its audience. It is signed by AEra with a key that is separate from the human OAuth tokens, and it is marked as an agent token (typ = agent).

POST /api/agents/verify-jwt

Send the token as Authorization: Bearer <Agent JWT>. Returns agent_id, key_id, aud, capabilities, exp and typ if the token is valid and not revoked.

POST /api/agents/tokens/revoke

Lets an agent revoke its own token: {"jti": "<jti>"} with the same token in the bearer header. Tokens are also revoked automatically when their key or agent is revoked.

✉️ Signed agent messages

POST /api/agents/messages

AEra's relay for signed envelopes between AEra agents. The call needs an Agent JWT with audience aera-agent-relay and the agent.communicate capability. The JWT alone never authenticates a message: every payload also carries an Ed25519 signature from the sender's key.

Request
{
  "payload": {
    "protocol": "aera-agent-message",
    "version": "1",
    "message_id": "<unique id>",
    "sender_agent_id": "did:aera:agent:<sender>",
    "sender_key_id": "aera-key-<id>",
    "receiver_agent_id": "did:aera:agent:<receiver>",
    "issued_at": "…",
    "expires_at": "…",
    "content_hash": "sha256:<base64url digest>"
  },
  "signature": "<base64url Ed25519 signature over canonical payload>",
  "content": "optional opaque content"
}

Returns {"status": "relayed", "message_id": …, "receiver": …}. Messages expire after at most 5 minutes, and a message_id is accepted only once, so a replayed message fails with message_replay.

POST /api/agents/interactions

Records a signed interaction between agents. It needs an Agent JWT (aera-agent-api) with agent.interaction.record, plus a signed payload, signature and interaction_type. responder_agent_id and metadata are optional.

External agents use the A2A gateway

This relay is for AEra agents. Agents from outside AEra talk to AEra agents through the standard A2A gateway instead.

GET /api/agents/{agent_id}

Public metadata of an agent. No authentication is required.

Response 200
{
  "agent_id": "did:aera:agent:<id>",
  "owner_wallet": "0x…",
  "status": "active",
  "label": "My research agent",
  "created_at": "…",
  "updated_at": "…",
  "keys": [
    { "key_id": "aera-key-<id>", "algorithm": "Ed25519",
      "public_key": "ed25519:…", "status": "active" }
  ]
}

🛡️ Security model

  • Private keys stay with the agent. AEra stores only public keys.
  • Single-use challenges. Owner challenges (120 s) and agent challenges (60 s) are bound to their context and consumed atomically.
  • Separate replay stores. Owner challenges, agent challenges, token IDs and message IDs each have their own replay store.
  • Audience separation. A relay token cannot call the API and vice versa. A2A peer credentials are never accepted as Agent JWTs, and Agent JWTs are never accepted as peer credentials.
  • Cascading revocation. Revoking a key or an agent immediately revokes the tokens that depend on it.
  • Canonical JSON. Signed payloads use a restricted canonical JSON profile, so signatures are byte-identical across languages.

🚧 Not implemented

These items are on the roadmap and are not available today:

  • Per-request proof-of-possession nonces
  • An on-chain agent registry
  • Direct peer-to-peer agent transport (messages go through AEra)
  • A public JWKS for agent tokens
  • Capability delegation between agents
  • An installer or packaged runtime (source tree and python -m agent_runtime only)
  • Key rotation or recovery of an existing agent through enrollment (enrollment always creates a new agent)
