A2A Gateway

The AEra A2A gateway lets agents outside AEra talk to AEra agents using the open Agent2Agent (A2A) protocol, without becoming AEra agents themselves.

Endpoint

POST /api/a2a

Discovery

/.well-known/agent-card.json

Protocol

A2A 0.3 · JSON-RPC 2.0

Method

message/send
The gateway is a door, not a promise

Reaching the gateway does not make a caller trusted and grants no permissions by itself. AEra resolves every target agent from its own records, never from what the caller claims.

The runtime is the process that actually is the agent: it holds the agent's private key, authenticates to AEra and answers messages. The gateway forwards messages to it over an authenticated internal channel. Inbound message text is treated as untrusted data: it cannot grant capabilities or trigger actions.

🔎 Discovery

A2A clients start by reading the public Agent Card at https://aeralogin.com/.well-known/agent-card.json. It describes the endpoint, transport, supported skills and the accepted security scheme.

📨 Sending a request

Send a JSON-RPC 2.0 message/send call. Name the AEra agent you want to reach in metadata.aera_target_agent. Each messageId must be unique.

cURL
curl -X POST https://aeralogin.com/api/a2a \
  -H "Content-Type: application/json" \
  -H "A2A-Version: 0.3" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "message/send",
    "params": {
      "message": {
        "kind": "message",
        "role": "user",
        "messageId": "b3f1c2de-0000-4000-8000-000000000001",
        "parts": [{ "kind": "text", "text": "agent.read.profile" }],
        "metadata": { "aera_target_agent": "did:aera:agent:<id>" }
      }
    }
  }'
Response 200
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "kind": "message",
    "messageId": "…",
    "role": "agent",
    "parts": [
      { "kind": "text", "text": "…" },
      { "kind": "data", "data": { "…": "…" } }
    ]
  }
}

If you hold an AEra peer credential, add Authorization: Bearer <your peer credential>. Keep the credential secret and never put it in the message body.

🌐 External peers

Every caller of the gateway is an external peer: a separate identity domain from AEra agents and from AEra humans.

  • Without a credential, a caller is an anonymous external peer. Whether anonymous calls are accepted depends on the gateway's authentication policy, which the Agent Card declares.
  • With a valid AEra peer credential, the caller is an authenticated external peer with a stable peer identity.
  • An external peer never becomes an AEra agent, whatever it claims about itself and however long it behaves well.
Human ≠ Agent ≠ External peer

Each has its own credentials. AEra Agent JWTs are refused at the gateway, and peer credentials are refused by the Agent API.

🎟️ Peer credentials

An agent owner issues a credential to a named external peer through AEra's owner dashboard API, which requires the owner's signed-in dashboard session. There is no self-registration. The credential is handed to the peer out of band.

Scoped

Limited to specific agents (which must belong to the issuing owner) and specific skills.

Expiring

Every credential has an expiry date.

Revocable

The owner can revoke it at any time, effective on the next request.

Stable peer identity

The peer identity survives credential rotation, so history stays with the peer. To rotate, issue with rotate_cred_id set to one of your own credentials, then revoke the old one. The peer identity is always assigned by AEra and cannot be chosen by the caller.

The credential is an opaque bearer secret, shown to the owner once at issuance. AEra stores only a one-way hash of it.

✅ Authorization

Authentication answers who is calling. Authorization is a separate step that decides what they may reach:

  1. The target agent must exist, be active and hold the capability for the requested skill.
  2. For an authenticated peer, the target agent and skill must both be inside the credential's scope.
  3. Expired or revoked credentials are refused. No other signal can revive them.

🔁 Replay protection

Each inbound messageId is accepted once. A duplicate within the replay window (10 minutes) is refused, and requests with timestamps that are too old or too far in the future are rejected.

⏱️ Rate limiting

The gateway checks a global budget and a per-caller budget before it reads the request body, and a per-target budget before it contacts an agent. Refused requests get HTTP 429 with a Retry-After header and JSON-RPC error -32010. The response does not reveal which limit was hit.

📈 Trust assessment

AEra derives trust assessments from observable evidence. For authenticated external peers, AEra can record security metadata about requests it has already authenticated (successful requests, denied authorizations, rejected replays, rate-limit hits, invalid requests) and compute an assessment from that evidence.

Level

untrusted, unknown, minimal, limited or established. New peers start as unknown.

Confidence

How much evidence exists. A high level requires enough evidence, so silence is never mistaken for a good reputation.

Derived, not declared

Trust claims sent by a caller are ignored. An owner's standing is one bounded input and never decides the result alone.

Private

Only the owner of the agents a peer talks to can see the assessment. It is not published on the public Agent Card.

Monitoring, not enforcement

Trust assessment runs independently of authentication and authorization. It does not replace credential validation, scope checks, revocation, replay protection or rate limiting, and it does not change any access decision today. There is no enforcement mode. Evidence is only recorded while the operator runs the gateway in observation mode.

📏 Limits & scope

  • Request body: at most 64 KB. Up to 16 parts, 8,000 characters of text and 20 metadata keys.
  • Input: text/plain. Output: text/plain and application/json.
  • Not supported: streaming (message/stream), push notifications, task retrieval or cancellation (tasks/*), the authenticated extended card, gRPC and HTTP+JSON transports.
